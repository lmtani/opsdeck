# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal, single-user devops dashboard ("OpsDeck"). It serves customizable link cards (shortcuts to GCP projects, dashboards, tools), runs saved log queries against log sources (Google Cloud Logging for now) and follows GitHub org activity through saved feeds. Backend is Python/FastAPI; frontend is static vanilla JS (no build step). UI text, API messages and event wording are in English; dates and times use `LOCALE` from `web/js/ui.js` (en-US, 24-hour clock).

Runs locally (MySQL, logs via the Cloud Logging API with the user's Application Default Credentials, command cards enabled) or in a container built from the distroless `Dockerfile`; `docker-compose.yaml` runs it with its own MySQL. The container mode is plain env configuration: the ADC file at `GOOGLE_APPLICATION_CREDENTIALS` (mounted from `secrets/` by compose), `DASHBOARD_COMMANDS=off`, the MySQL service via `DASHBOARD_DB_*`, `GITHUB_TOKEN` from the environment and a volume at `data/images/` (the image ships that directory owned by the runtime user so a fresh volume is writable). `.github/workflows/ci.yml` runs the tests on pushes to `main` and on PRs, and builds and smoke-tests the image for `linux/amd64` and `linux/arm64` (QEMU); the Dockerfile copies CPython's libraries from the build platform's multiarch directory, so never hard-code `x86_64-linux-gnu`. Repository language is English: code, comments, docs and commit messages.

## Commands

```bash
uv run main.py                          # Serve at http://127.0.0.1:8765 (DASHBOARD_PORT/DASHBOARD_HOST override)
uv run uvicorn main:app --reload --port 8765   # Dev mode with auto-reload
uv run pytest -q                        # Run all tests
uv run pytest tests/test_services.py -q # Run one test file
uv run pre-commit install               # Once per clone: run the hooks below on every commit
uv run pre-commit run --all-files       # ruff (lint + format), mypy, Biome (web/), gitleaks, file hygiene
uv run migrate.py                       # Apply pending DB migrations explicitly
uv run migrate.py --import-json         # ...and import legacy data/*.json records
uv add <package>                        # Add a dependency
```

API docs are served at `/api/docs` when running. The local MySQL is the shared container on port 13306 (the config default): `mariadb -h 127.0.0.1 -P 13306 -u root -p1234 opsdeck`.

## Architecture

Ports and adapters (clean architecture) with strict layer direction — outer layers depend on inner, never the reverse. The ports are declared in `app/domain/`, `app/infrastructure/` holds the driven adapters that implement them, `app/presentation/` is the one driving adapter (HTTP), and `app/bootstrap.py` wires them together:

- `app/domain/` — one module per bounded context, each holding its entities and its **ports**: `links.py` (`Link`, `LinkKind`, `LinkRepository`, `CommandRunner`, `ImageStore`, whose `load` reads an upload back for exports), `logs.py` (`LogSource` — a `LogSourceKind` (only `gcp` today) plus a `config` dict whose required keys `SOURCE_CONFIG` lists per kind (gcp: `project`); its kind is fixed after creation, since the filters on it are written in that kind's language — `LogFilter` (points at a source by `source_id`), `LogQuery` (expression, freshness, limit and `Refinement`s: a `path` of segments, a scalar `value`, `negate`), `Freshness`, `LogEntry`, `LogSourceRepository`, `LogFilterRepository`, and the `LogProvider` port, one per kind: `expression(query)` spells the refinements in the backend's language, `query`/`describe`/`console_url` take the `LogSource` and the query), `github.py` (`FeedSpec`, `GithubFeed`, `GithubEvent` with its typed `details` value objects, the `EventKind`/`ItemState`/`ReviewState`/`EventSource` enums, `GithubFeedRepository`, and the `GithubProvider` port, whose `activity(spec, realtime_since)` returns an `ActivitySnapshot` — viewer, one `GithubEventBatch` per source, near-real-time PR events, warnings, `Quota` — plus `org_repos`, `pull_requests`, `contributions(spec, since)` (a `ContributionsSnapshot` of `Contribution`s: login, `ContributionKind` commit/pr/review/issue, repo, time) and `event_context(subject)`, which returns an `EventContext`: the full text rendered as HTML, author, for code comments path/line/`diff_hunk`, a `thread` of `ThreadComment`s and, for PRs, `PullStats` with `Label`s and `Reviewer`s), `settings.py`. Shared pieces: `errors.py` (`DomainError` → 404/422 for not-found/validation; `ExternalServiceError` → 502 for a failing port: `LogProviderError`, `GithubError`, `CommandError`), `common.py` (ids, `utc_now`, `parse_timestamp`/`format_timestamp`), `repository.py` (generic `Repository[T]` port) and `ordering.py` (`Orderable` protocol + `ordered`/`next_position`). **Entities enforce their invariants in `__post_init__`** (an invalid `Link`, `LogSource`, `LogFilter`, `LogQuery`, `Refinement`, `FeedSpec` or `GithubFeed` cannot be built, not even from a row) and are built/edited through `new(...)`/`update(...)`, which trim and validate before changing anything; timestamps are aware `datetime`s. `github_rules.py` holds the pure GitHub rules: conventions shared by the parser and the use cases (compare URLs, bot logins, wording), the timeline logic (`keep_event`, `is_unseen`, `collapse_bursts`, `coverage_start`, `merge_realtime`) and the contributors buckets (`contribution_kinds`, `daily_contributions`: per login, local day, kind and repo). No I/O, no framework imports.
- `app/application/` — use cases, one module per context: `links.py` (`LinkService`, `CommandService`, `ImageService`), `logs.py` (`LogSourceService`: names unique case-insensitively, a source still used by a filter cannot be deleted; `LogFilterService`, which checks the filter's source exists; `LogQueryService`, which picks the provider by the source's kind and returns a `LogResult`: the source, the refined `expression`, the CLI `command`, the `console_url` and the entries), `github.py` (`GithubFeedService`, `GithubActivityService`), `settings.py` (`SettingsService`), `sharing.py` (`SharingService`: export/check/import of a portable bundle, see Frontend); `common.py` has `apply_order`. Services are thin orchestration (`create_x(**fields)` → `Entity.new(...)` → save); validation lives in the entities. Depend only on domain ports and rules; raise domain errors (`ValidationError`, `NotFoundError`, `LogProviderError`, `GithubError`, `CommandError`).
- `app/infrastructure/` — the driven adapters, one subpackage per outside system: the first level is the capability, the second the concrete system, so a new backend for an existing port (a CloudWatch log source, a second storage) is a sibling folder plus a line in `bootstrap.py`. Each package's `__init__.py` says which ports it implements and re-exports what `bootstrap.py` needs: `persistence/` (`rows.py`; `mysql/`: `connection.py`, `repositories.py`, `migrations.py`; `json_files/`: `store.py`, `repositories.py`, `legacy.py` with the upgrade of pre-source filters), `logs/` (one subpackage per `LogSourceKind`, each with `provider.py`, `expression.py` for the backend's query language and `entries.py` for its entries; `gcp/` today), `github/` (`provider.py`, `parsing.py`, `html_sanitizer.py`) and `host/` (`commands.py` with both command runners, `images.py`). In detail: MySQL repositories (PyMySQL, short-lived connections via `MySqlConnectionFactory`), JSON-file repositories (legacy/fallback), both mapping rows through `rows.py` (enums ↔ values, datetimes ↔ ISO-8601 UTC text, the feed's lists; MySQL joins those lists with commas), `CloudLoggingApiProvider` (the provider of `gcp` sources, reading the source's project; it spells refinements as Cloud Logging clauses, quoting path segments that are not identifiers, and builds the `gcloud logging read` command and the Logs Explorer URL; Cloud Logging API client via ADC, from `GOOGLE_APPLICATION_CREDENTIALS` or the well-known location `gcloud auth application-default login` writes; the app never runs the `gcloud` CLI, `describe` only builds the equivalent command for the copy button; one client per queried project, so no `GOOGLE_CLOUD_PROJECT` is needed; credentials are loaded and refreshed up front through injectable `load_credentials`/`make_client`, so auth problems fail fast, and google-auth/api-core exceptions become `LogProviderError`s that say what to do; `is_available` checks the credentials file offline; the filter language, the freshness cutoff, the gcloud command and the Explorer URL are pure functions in `logs/gcp/expression.py`, entry parsing is `logs/gcp/entries.py`), `SubprocessCommandRunner` and `DisabledCommandRunner` (containers), `GithubApiProvider` (REST events API + search API + batched GraphQL for PR title/state; `activity()` reads the org feed or each repo in parallel, turning a failing repo into a warning unless all fail, and warns when an org feed falls back to public events; `token_status()` (→ `GET /api/github/token`, shown in the GitHub sidebar and the top-bar dot) classifies the token by prefix, reads classic/OAuth scopes from `X-OAuth-Scopes`, and turns 401s, SAML and fine-grained-policy 403s into instructions; conditional GETs with an in-memory ETag cache, pagination via the Link header; each source's event window is remembered (`_event_window`), so a refresh walks the pages only until it meets a known event id (usually page 1 alone, often a free 304), puts the new events on top and drops what falls past the page limit (flagging the source truncated), with a full re-read every 15 min (`events_resync_seconds`); the token comes from the injected `token_source`, with `resolve_github_token` falling back to the local `gh auth token`; event normalization in `github/parsing.py`), `LocalImageStore`, the migration runner (`persistence/mysql/migrations.py`) and `github/html_sanitizer.py` (an nh3 allowlist applied to the `body_html` GitHub renders before it reaches the page).
- `app/presentation/` — FastAPI routes (`api.py`) and Pydantic schemas. The `*Out` models are the response contract and read entities with `from_attributes` (events, activity and contributions are built explicitly; `Quota` becomes `rate_remaining`/`rate_limit`). Log sources live under `/api/log-sources`. Saved filters/feeds run through `POST /api/filters/{id}/query` (an optional body carries `refinements` for that run) and `POST /api/github/feeds/{id}/query`; `/api/logs/query` (a `source_id` plus the query) and `/api/github/events/query` are ad hoc only. Maps `DomainError` to 404/422 and `ExternalServiceError` to 502 via exception handlers, and any other exception to a 500 whose `detail` names the error (never a bare "Internal Server Error"); `/api/health` reports `logs` (whether every kind of source in use can be queried; `null` without sources, which hides the top-bar dot) and `github`. Mounts static files last so `/api` keeps precedence.
- `app/bootstrap.py` — **composition root**, the only place that wires interfaces to implementations and the only place that reads the environment (`Settings.from_env()`; `build_services`/`create_app` accept a `Settings` for tests). Storage backend is chosen here: MySQL by default, JSON files with `DASHBOARD_STORAGE=json`.
- `app/config.py` — the frozen `Settings` dataclass and `Settings.from_env()`: MySQL connection (`DASHBOARD_DB_HOST/PORT/USER/PASSWORD/NAME`, defaulting to local root/1234 on 13306, database `opsdeck`; the `MySqlSettings` type lives with the connection factory), the ADC file (`GOOGLE_APPLICATION_CREDENTIALS`, empty = the well-known location), the container switch `DASHBOARD_COMMANDS=on|off` (default `on`), and `GITHUB_TOKEN`/`GH_TOKEN` (classic PAT with `repo` + `read:org`; empty = local `gh` login). Adapters never read `os.environ`.

## Persistence & migrations

Data lives in MySQL 8: tables `links`, `log_sources` (`config` as JSON text), `log_filters` (`source_id`), `github_feeds` (repos and event kinds as comma-separated text), `settings` (key/value rows), `schema_migrations`. Migrations are plain numbered `.sql` files in `migrations/mysql/` (e.g. `0007_add_x.sql`), applied in filename order and tracked in `schema_migrations`. Statements are split on `;` so keep semicolons out of string literals. Pending migrations run automatically on app startup and can be run explicitly with `uv run migrate.py`. To change schema: add new files, never edit applied ones. `limit` is a reserved word in MySQL, so it is backtick-quoted. Upserts use `ON DUPLICATE KEY UPDATE`. `created_at`/`last_seen_at` columns hold ISO-8601 UTC text (older rows end in `+00:00`, newer in `Z`; both parse) — entities hold aware datetimes and sort in Python, never rely on the SQL order. Uploaded card images stay on disk in `data/images/` (gitignored; in containers that path is a volume).

Quality gates live in `.pre-commit-config.yaml` and run in CI (`lint` job, plus a gitleaks scan of the whole history). Python: ruff with line length 110 and the rule set in `pyproject.toml` (bandit checks included; justified exceptions are `# noqa: <rule>` with the reason next to them), `ruff format`, and mypy over `app/`. Python tools run through `uv run --frozen`, so their versions come from `uv.lock`. Frontend: Biome (`biome.json`) lints `web/` and formats the JS at 100 columns; CSS formatting is off to keep the file's one-line rules, and CSS/HTML lint exceptions use `biome-ignore` comments with a reason. Never apply Biome's `--unsafe` fixes blindly: one of them drops `!important`.

Tests (`tests/`) use the in-memory fakes of the domain ports in `tests/fakes.py` (plus builders of GitHub events) — no files, subprocess, Cloud Logging or network. One service test file per context, `test_entities.py` for the invariants, `test_github_rules.py` for the pure rules, parser/provider tests over `httpx.MockTransport`, and `test_api.py` drives the FastAPI app with `TestClient` over the same fakes (status codes, error mapping, the `/order` and `/unseen` routes that must beat `/{id}`), and `test_config.py` covers `Settings.from_env`. `FakeGithubProvider` builds snapshots from plain dicts and mirrors the adapter's partial-failure policy. Follow that pattern: new behavior gets a service test, new routes get an API test.

## Frontend

`web/` is served as-is (ES modules, no bundler). `css/app.css` defines four themes as CSS-variable blocks under `[data-theme="..."]` (midnight, phosphor, ember, paper); theme choice persists to both localStorage and the backend settings. Adding a theme means a new variable block in CSS plus an entry in `web/js/theme.js` `THEMES`. Fonts: Chakra Petch (display), IBM Plex Sans (body), IBM Plex Mono (data), loaded from Google Fonts.

The app is an installable PWA: `web/manifest.json`, the icons in `web/icons/` (`icon.svg` is the source; the PNGs and the maskable variant, whose mark sits inside the 80 % safe zone, are rendered from it), and `web/sw.js`, registered by `main.js`. The service worker caches nothing (every view is live data) and only answers a failed page load with an offline notice; API calls and assets bypass it. `theme.js` sets `<meta name="theme-color">` to the theme's `base` (the installed app's title bar), and `github.js` mirrors the tab's unseen count on the app icon with `navigator.setAppBadge`.

JS modules: `api.js` (fetch wrapper), `ui.js` (modals/toasts/confirm), `links.js` (cards view), `logs.js` (log sources, filters + log entries view), `github.js` (feeds + activity timeline), `github-contributors.js` (the contributors mode of a feed), `github-network.js` (the network mode: people ↔ repositories), `github-context.js` (the side panel with an event's full context: renders the sanitized `body_html` and diff hunks, ↑/↓ steps through the visible events, pushes the page aside on screens ≥ 1180 px), `notifications.js` (desktop notifications for feeds), `share.js` (export/import of cards, filters and feeds), `tooltip.js` (the one floating tooltip every view shares: `setupTooltips(...containers)` wires containers, `tooltipContent` is the WeakMap of rich-tooltip builders, which must escape what they interpolate), `theme.js`, `main.js` (bootstrap, tabs, clock, health check; dispatches a `view:change` event on `document` when the tab changes). Always escape user content with `escapeHtml` from `ui.js` when building HTML strings.

GitHub feeds (`github.js`): a feed is one org plus an optional repo list (empty = the org "dashboard" of the token's user, which includes private repos) and optional event kinds (`push`, `pr`, `review`, `comment`, `issue`, `branch`, `release`, `other`). The service merges/sorts/dedupes events, drops bots and the viewer's own actions when asked, fills PR titles via GraphQL (the events API no longer sends them) and folds bursts (consecutive pushes to one branch, consecutive code-review comments on one PR) into one event with `count`. Because the events API publishes with a delay of up to hours, the adapter's `activity()` also runs a GraphQL PR search (`updated:>=` the last 12 h, org or repo qualifiers split under the 256-char search limit, 60 s cache) and turns openings, merges and reviews into events with `source = EventSource.SEARCH` (shown with ⚡); `merge_realtime` drops a searched event once the events API publishes the same type/PR/verb/actor within 10 min; searched events carry `source = EventSource.SEARCH`. Events are never stored. Each event may carry an `EventSubject` (type, repo, number and/or item id: the PR, issue, comment, review or release it is about; folded code comments keep one each), set by the parser; `POST /api/github/events/context` takes that subject back, the adapter builds the REST path from it (never from a client URL) and reads it with the html media type, not conditionally, because signed image URLs in `body_html` expire. The event's own `body` stays a 400-char excerpt. A missing item becomes a 404 (`NotFoundError`). Around the subject the adapter also reads (up to 3 pages each): for a review comment its whole thread (the root, fetched when the comment is a reply, plus the PR's review comments listed `since` the root; GitHub points every reply at the root), for a review its line comments, for a PR its reviews, reduced by `pull_stats_from_api` to each reviewer's latest verdict (a later comment does not undo an approval; a re-requested reviewer counts as pending). Label colors are validated as six hex digits before they reach a `style`. `GithubFeed.mark_seen` only moves forward; a saved feed's query (`POST /api/github/feeds/{id}/query`) flags each event `is_new` against that mark and returns `unseen`, so the UI only renders the flags, highlights them, and marks the newest event as seen when the feed, the tab or the page is left ("✓ visto" clears the flags locally). `POST /api/github/feeds/preview` normalizes a feed spec (canonical repo names, kinds) for the modal, so the frontend never re-implements that rule. A refresh re-renders the timeline only when its `activitySignature` changed, and animates just the events it brought (`is-arrived`); `setBusy` drives the thin `#gh-progress` bar and the spinning refresh icon for both modes, and the first load of each mode shows a skeleton shaped like it (timeline rows; the grid with a wave and the elapsed seconds). Refinements (repo/kind/author chips) are client-side only; kind/state labels are presentation text and live in `github.js`. Each day header carries a volume histogram of 48 half-hour bins (sums `count`, follows refinements, one scale for all days); hovering a bin shows its contributors and kinds (rich tooltips are registered per element in `tooltip.js`'s `tooltipContent`). Below it, a contributors strip (`dayContributors`/`contributorsNode`) lists the day's authors by weighted count (8 shown, "+N" expands, kept per day in `view.peopleOpen`); it is computed from the events matching every refinement except the author one, so it acts as a facet: clicking toggles the author refinement and the others stay visible, dimmed. Hovering a person shows their kinds, repos and first–last time and draws their share over the dimmed histogram (`focusHistogram`, the `--mine` height of each column). A day that starts before `coverage_start` is labeled partial. Hours before `GithubActivity.coverage_start` are hatched as "sem dados": the events API caps each source at ~300 events and serves them in processing order (stragglers weeks older appear mid-page), so the provider flags a source as truncated when it has more pages or reaches the cap, and the service takes the median creation time of each truncated source's last 30 events in API order (the ones processed last, which sit at the real boundary), keeping the latest across sources.

Contributors mode (`github-contributors.js`, the `timeline | contributors` switch, remembered in localStorage with the 2/4/8-week period): `POST /api/github/feeds/{id}/contributions` with `days` (1–92) and the browser's IANA `tz` returns `DailyContribution` counts (login, local day, kind, repo) over [since, until]; the service turns local midnight `days − 1` days ago into the instant it asks the provider for (`tzdata` ships the zone database, the distroless image has none), and `daily_contributions` applies the feed's kinds (push → commit; comment/branch/release have no counterpart) and bot filter, never `hide_own`, and counts a person's reviews of one PR once per day (each reply in a review thread is a "commented" review; the day list still shows them all). GitHub's own `contributionsCollection` is not used: it hides other people's private-repo work (and even the viewer's, as "restricted"), so the adapter reads the repositories: the default-branch history (GraphQL, 10 repos per query, merge commits skipped, commits whose email has no account counted in a warning) of the feed's repos or of the org repos pushed since `since`, plus a PR search (`updated:` cut into 7-day slices so they run in parallel and stay under the 1000-result cap, deduplicated by node id; PR openings and reviews by anyone but the author) and an issue search (`created:>=`); everything runs in one thread pool and the snapshot is cached 10 min (`fetched_at` is the read time). The grid colors cells on one sqrt scale with `--kind-*` root tokens (one kind picked → its color); kind/repo chips are client-side facets; rich tooltips (cells, the team strip, the total + kind-mix cell of each row, the "timeline" bracket) reuse `tooltip.js`'s `tooltipContent`, passed in as `tooltips`. The bracket marks days from `timelineStart` (`coverage_start`, else the oldest event); clicking a cell opens a bar that lists what the person did that day and sends the day to the timeline as `actor` + `day` refinements (`day` is a local `YYYY-MM-DD`; neither is saved into a feed) or to GitHub search. The list comes from `POST /api/github/feeds/{id}/contributions/day` (the grid's `days` and `tz` plus `login` and `day`, so the provider answers from the cached read; `contributions_on` picks the items, newest first): each `Contribution` carries the commit headline or PR/issue number and title, a github.com URL (anything else is dropped by the parser) and, for a review, its `ReviewState`; the UI folds the reviews of one PR into one row with a count per state, since every reply in a review thread is a "commented" review.

Network mode (`github-network.js`, the third position of the `timeline | contributors | network` switch) draws the same `/contributions` response (the provider's 10 min cache makes the second read cheap; the period switch calls `setDays` on both modes, reloading only the visible one and making the hidden one forget its data) as a bipartite people ↔ repositories graph: `buildGraph` aggregates the `DailyContribution` rows under the kind/repo chips into person nodes (total, kind mix, links sorted by count, `bridge` when linked to 2+ repos), repo nodes (the feed's listed repos stay as empty dashed nodes; `concentrated` when the top person holds ≥ 60 % of at least 5 contributions) and links (`personShare`, `repoShare`); a link is drawn only when it holds at least `minShare` (slider, default 5 %, `opsdeck.github.network.share`) of the person's work, and people left without links are counted in the status line. The physics is the module's own small simulation in the manner of d3-force (`createSimulation`: springs with a rest length from the chosen share, `opsdeck.github.network.length`, O(n²) repulsion, collision, gravity stronger on the canvas' short axis); the first frame is settled synchronously (160 steps, 300 under reduced motion) and node objects persist in `placed`, so filters, the threshold and the period keep every node where it was; a dragged node is pinned (`fx`/`fy`, a dot marks it, double-click releases) and the view fits itself until the user pans or zooms (ctrl + scroll or the corner buttons; plain scrolling keeps scrolling the page). Hovering or pinning (click; Esc clears) a node lights its neighbourhood (`litSet`/`applyFocus`, class toggles only) and the side panel shows it (`renderPanel`, keyed so it only rebuilds when the subject changes): at rest the bridges and the concentrated repositories, for a person their repositories by share with "→ timeline" (`openRefined` with an `actor` refinement), "▦ contributors" (`contributors.focus(login)`) and GitHub, for a repository its people by share and a bus-factor note; panel rows and repo chips light their node on hover (`rowFocus`). Tooltips of nodes and links go through `tooltipContent` like the grid's (the SVG groups carry `data-tooltip`), so the app's one tooltip places them. Avatars are `<image>`s clipped round; rings and the panel's mix bars take their colors from the `.kind-*` classes.

Sharing (`share.js`, `app/application/sharing.py`): the ⇅ button of each view (Links toolbar, the Logs and GitHub sidebars) opens Export/Import. Export puts the view's own list in picking mode (`registerShare` intercepts clicks in the capture phase; a `MutationObserver` keeps the picked look across re-renders) with a bottom bar to save a `.json` file or copy it; `POST /api/share/export` returns the bundle (`opsdeck: 2`, `links`, `log_filters`, `github_feeds`, editable fields only, uploaded images inlined as data URIs; a filter carries its `source` as name, kind and config, never the id). Version 1 files, whose filters named a GCP `project`, still import. A filter's source is matched by kind and config (`LogSource.same_place`): an existing one is reused, a missing one is created on import under a free name. Import takes a file (picker or dropped anywhere) or pasted text, asks `POST /api/share/check` for each item's status (`new`, `conflict` = same name in that type, case-insensitive, or `invalid` with the entity's message) and shows a review: per conflict "keep both" (a numbered copy) or "replace" (overwrites fields, keeps id, position and a feed's mark); command cards come unchecked with their command shown. `POST /api/share/import` validates every chosen item before writing any; the views reload and the imported items glow (`is-imported`).

Desktop notifications (`notifications.js`, Web Notifications API) are browser-only state: which feeds notify and, per feed, the newest event already announced live in localStorage (`opsdeck.github.notify`, `opsdeck.github.notified.<id>`), so nothing is announced twice and turning a feed on does not replay its backlog. `github.js` polls `/api/github/feeds/unseen` on a 60 s tick: every 5 min while the page is visible, every 2 min even in a background tab when some feed notifies; for each notifying feed with unseen events that the user is not looking at, it runs the feed and calls `announce`, which notifies only events with `is_new` newer than the mark (one notification per feed, replaced through its `tag`). Turning a bell on sends a `confirmEnabled` notification right away, so the user sees that notifications reach the desktop. The browser only offers notifications in a secure context (HTTPS or localhost). The "live" switch (`AppSettings.github_polling`, saved in the backend) pauses all of that background work, notifications and the auto refresh included; `PUT /api/settings` is a partial update (`SettingsUpdate`), so the theme picker does not reset it. Settings booleans come back from MySQL as text and are parsed in `rows.values_to_settings`.

`logs.js` keeps the sources and filters of the sidebar (a source is presented through `SOURCE_KINDS`: form fields, tag, syntax label, whether it has `traces`; with no source the empty state leads to creating one) and a single `view` object for the results panel: mode `filter` (a saved filter on its `source`, plus ad-hoc `refinements` added by clicking severity/resource/detail chips; each is `{path, value, negate}` with the path as an array, because keys may hold dots or slashes, sent with the saved filter's query so the backend writes the clauses; the result's `expression` is what "Save as new filter" saves, and its `console_url` drives the "open in" button) or mode `trace` (only for kinds with `traces`, i.e. GCP, whose Cloud Logging clauses `logs.js` still writes: every entry sharing the clicked row's `trace`, or `operation.id` as fallback, queried with an explicit ±1 h timestamp window so freshness is ignored; "other sources" repeats the query in every other source of the same kind, one per project). A trace view stores its `parent` view + entries so "back"/Esc restores without re-querying. `trace`, `span_id` and `operation_id` are first-class fields on `LogEntry`. Above the entries, `renderHistogram` draws 60 columns stacked by severity band (error, warning, info, debug/default; the tooltip lists each severity) over the filter's freshness window up to the query time (`view.queriedAt`), or over a trace's own entries; when a filter returns its full `limit` the bars start at the oldest entry and the legend says the window was clipped. Clicking a column scrolls to its first entry (`is-flash`, on `.entry-row`: the entry's own `entry-in` animation is what makes it visible). While a query runs the slot shows breathing skeleton bars (`showHistogramSkeleton`); a fresh result grows its columns in (`paintEntries({ rise: true })`), while re-renders (format, back) do not animate.
